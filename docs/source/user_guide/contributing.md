# Contributing

Quadrants development now uses the CMake + Haxe/HashLink workflow.

## Build

```bash
cmake -S . -B build/dev \
  -DQD_WITH_HASHLINK=ON \
  -DQD_HASHLINK_ROOT=/path/to/hashlink \
  -DQD_WITH_LLVM=ON
cmake --build build/dev --target quadrants.hdll
```

The `quadrants.hdll` target builds the required host runtime bitcode for the current host. Add `-DQD_BUILD_HASHLINK_TESTS=ON` when you want CTest to register the Haxe/HashLink tests. Disable `QD_WITH_HASHLINK` when validating a core-only build on a machine without HashLink.

## Test

```bash
ctest --test-dir build/dev --output-on-failure
```

The HashLink CTest suite compiles the Haxe tests, runs a CPU `hl` smoke test, and checks macro compile-fail diagnostics.

## Documentation

Build the unified documentation site (Haxe API reference plus the Markdown guides in `docs/source/`) with a single target. The site is generated by `quadrants-dox`, a HashLink-running fork of Dox registered as a haxelib:

```bash
# one-time: install the Dox fork and its pinned dependencies
haxelib git hxtemplo https://github.com/Simn/hxtemplo 4b9ec0c07e9ec619c7c414c3a72af4be63d820cc
haxelib git hxparse   https://github.com/Simn/hxparse 876070ec62a4869de60081f87763e23457a3bda8
haxelib git hxargs    https://github.com/Simn/hxargs  1d8ec84f641833edd6f0cb2e4290b7524fd27219
haxelib install markdown
haxelib dev quadrants-dox ../quadrants-dox   # or: haxelib git quadrants-dox https://github.com/yolkarian/quadrants-dox.git
make -C docs html
```

`make html` generates Haxe XML from `bindings/hashlink/haxe`, then runs `quadrants-dox` on HashLink (`hl run.hl`) in one pass: it renders the API pages, folds in the Markdown guides from `docs/source/` (rewriting `.md` links to `.html` and linking type names in code spans to the API), injects a Guides + API-reference section into the sidebar nav, and writes the landing page. The output in `docs/build/html` is a self-contained site: `index.html` is the landing (rendered from `docs/source/index.md`), `api.html` is the Dox toplevel package listing, `user_guide/*.html` are the rendered guides, and `quadrants/**` are the API pages. Pushes to `dev` that touch `docs/`, the Haxe sources, or `.github/workflows/docs.yml` build the site on HashLink in the `docs` workflow and deploy it to GitHub Pages.

## Haxe package development

Register the source tree directly while iterating, and install the native bridge into the HashLink checkout used for local runs:

```bash
haxelib dev quadrants "$PWD/bindings/hashlink"
scripts/install_hashlink_native.sh \
  --build-dir "$PWD/build/dev" \
  --runtime-dir "$PWD/build/dev/runtime" \
  --hashlink-dir /path/to/hashlink
haxe tests/hashlink/v3/hashlink_v3_smoke.hxml -hl build/dev-v3-smoke.hl
/path/to/hashlink/hl build/dev-v3-smoke.hl
```

## CI

The main Linux workflow builds `quadrants.hdll`, installs the HashLink native setup, installs/registers the haxelib interface package, compiles the v3 Haxe tests, runs the v3 smoke suite, checks descriptor golden snapshots, and scans public `Dynamic` boundaries.
